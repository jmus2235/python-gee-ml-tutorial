# ASD-STE100 communication norm

Working norm: use ASD-STE100 for replies and for skill output. Never drop or soften a technical issue to keep the text simple. If no simple word exists, use the exact technical term.

## Priority

1. Technical accuracy and completeness come first.
2. ASD-STE100 style comes second.

If a simpler sentence removes a fact, a limit, a risk, or an error, do not use it. Use more sentences instead.

## Writing rules

- Use words from the ASD-STE100 dictionary, with their approved meanings. Example: use "start", not "commence"; use "make sure", not "ensure".
- Use technical names and technical verbs where necessary. Examples: `ee.Classifier.smileRandomForest`, "reflectance", "hyperspectral", "overfit", "cross-validate", "reproject".
- Spell out each acronym the first time that you use it in a chat, then give the acronym in parentheses. Example: "Airborne Observation Platform (AOP)". Do this again in each new chat.
- Use one word for one meaning. Use the same term each time for the same thing.
- Write short sentences: 20 words maximum for instructions, 25 words maximum for descriptions.
- Write one instruction in each sentence. Use the imperative ("Run the cell.", "Set the scale to 1 m.").
- Use the active voice.
- Use only these verb tenses: simple present, simple past, simple future.
- Do not use "-ing" forms as nouns or adjectives, except in technical names.
- Do not make noun clusters of more than three words. Rewrite them with "of", "for", or "in".
- Use articles ("the", "a", "an") and demonstratives where English permits them.
- Write one topic in each paragraph. Write six sentences maximum in each paragraph.
- Use vertical lists for sequences, options, and sets of conditions.
- Put a warning or a caution before the related instruction, not after it.

## Content that does not change

Keep these items exactly as they are. Do not simplify or paraphrase them:

- Code, code blocks, file paths, commands, and URLs.
- API names, function names, parameter names, asset IDs, and band names.
- Error messages, log output, and quoted text.
- Numbers, units, versions, and dates.

## Technical issues

- State each problem, risk, limit, and uncertainty. Do not omit one to make the text shorter.
- Give the cause and the effect when you know them.
- If you do not know something, say "I do not know" and say what you must examine to find out.
- Do not use soft words to reduce a problem ("a small issue", "slightly", "probably fine") unless they are accurate.
